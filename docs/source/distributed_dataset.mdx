# Distributed Datasets

LeRobot Dataset v3.0 supports controlled distributed **writing**.

## Supported Modes

- Distributed writes support a new or existing dataset, one driver, and one or more workers that share the target storage.

An existing dataset can be extended with new episodes, but it must not change after the driver creates the plan. Distributed writes do not support two drivers or mixing `save_episode()` with active distributed workers.

## Distributed Writes

The driver allocates every episode and output file before any worker writes data. A worker owns exactly one `DistributedEpisodeSpec`, writes its own Parquet and MP4 files, and returns a result. Only the driver publishes `meta/`.

```python
from lerobot.datasets.lerobot_dataset import LeRobotDataset

driver = LeRobotDataset.create(
    repo_id="my-org/assembled-dataset",
    fps=30,
    features=features,
    root="/shared/assembled-dataset",
)

plan = driver.create_distributed_write_plan(
    episode_lengths=[len(frames) for frames in all_episodes],
    episode_tasks=[[frame["task"] for frame in frames] for frames in all_episodes],
)

def write_episode(spec, frames):
    worker = LeRobotDataset.open_distributed_writer(
        repo_id="my-org/assembled-dataset",
        root="/shared/assembled-dataset",
    )
    worker.start_distributed_episode(spec)
    for frame in frames:
        worker.add_frame(frame)
    result = worker.save_distributed_episode(spec)
    worker.finalize()
    return result

results = [
    write_episode(spec, frames)
    for spec, frames in zip(plan.episodes, all_episodes, strict=True)
]
driver.commit_distributed_results(plan, results)
driver.finalize()
```

`start_distributed_episode(spec)` is required before the first `add_frame()`. It assigns the worker's temporary camera directory to the planned episode, preventing video-frame staging collisions.

Each distributed episode receives a unique data file and, for each video feature, a unique MP4 file. Workers writing different episodes do not contend for a shared output file. Use the persistent session described below when the scheduler may retry workers.

To append to an existing local dataset, open the driver in write mode before creating the plan:

```python
driver = LeRobotDataset.resume(REPO_ID, root=ROOT)
plan = driver.create_distributed_write_plan(
    episode_lengths=[len(frames) for frames in new_episodes],
    episode_tasks=[[frame["task"] for frame in frames] for frames in new_episodes],
)
```

The driver starts episode and frame ranges after the currently published totals, preserves existing task indices, and allocates files after every occupied data, video, and episode-metadata file. Commit merges the previous tasks, statistics, and episode metadata with the new worker results.

## Multiprocessing and Ray

The scheduling layer only needs to pass a spec and its frames to each worker:

```python
from multiprocessing import get_context

with get_context("spawn").Pool(processes=4) as pool:
    results = pool.starmap(
        write_episode,
        zip(plan.episodes, all_episodes, strict=True),
    )

driver.commit_distributed_results(plan, results)
```

Ray can use the same protocol:

```python
import ray

@ray.remote
def write_episode_remote(spec, frames):
    return write_episode(spec, frames)

results = ray.get(
    [
        write_episode_remote.remote(spec, frames)
        for spec, frames in zip(plan.episodes, all_episodes, strict=True)
    ]
)
driver.commit_distributed_results(plan, results)
```

LeRobot does not import or require Ray; Ray is only one possible scheduler.

### Complete Ray Write Example

The following script creates a small dataset using two or more Ray workers. The
driver creates the dataset and allocates the plan, workers write only their
assigned episodes, and the driver publishes the metadata after every worker succeeds.

All Ray workers must be able to read and write the same `ROOT` directory. The
current API persists and validates filesystem paths, so `ROOT` must also have
the same absolute path on the driver and every worker, even when they run on
different machines. For example, mount the same read-write-many volume at
`/shared/lerobot-demo` in every Kubernetes pod. Mounting the same volume at
`/driver/data` in one pod and `/worker/data` in another is not supported.

```python
# distributed_write_ray.py
from pathlib import Path

import numpy as np
import ray

from lerobot.datasets.lerobot_dataset import LeRobotDataset

REPO_ID = "my-org/distributed-demo"
ROOT = Path("/shared/lerobot-demo")

FEATURES = {
    "observation.state": {"dtype": "float32", "shape": (2,), "names": None},
    "action": {"dtype": "float32", "shape": (2,), "names": None},
}

# Replace this with frames from collection or conversion jobs. Every frame must
# contain the features declared above and a string-valued "task".
EPISODES = [
    [
        {
            "observation.state": np.array([frame_index, 1], dtype=np.float32),
            "action": np.array([frame_index, 2], dtype=np.float32),
            "task": "pick",
        }
        for frame_index in range(3)
    ],
    [
        {
            "observation.state": np.array([frame_index, 3], dtype=np.float32),
            "action": np.array([frame_index, 4], dtype=np.float32),
            "task": "place",
        }
        for frame_index in range(2)
    ],
]


@ray.remote(num_cpus=1)
def write_one_episode(spec, frames, session):
    worker = LeRobotDataset.open_distributed_writer(REPO_ID, root=ROOT, session=session)
    try:
        # Required before add_frame(): it gives this worker a unique staging
        # directory for the episode's images and videos.
        worker.start_distributed_episode(spec)
        for frame in frames:
            worker.add_frame(frame)

        # This writes only the files allocated by spec. It does not update meta/.
        return worker.save_distributed_episode(spec)
    finally:
        worker.finalize()


def main():
    ray.init(address="auto")

    # The driver can create a new dataset or resume an existing local dataset.
    driver = LeRobotDataset.create(
        REPO_ID,
        root=ROOT,
        fps=30,
        features=FEATURES,
        use_videos=False,
    )

    # Allocate global frame indexes, task indexes, and unique chunk/file paths
    # before starting any worker.
    plan = driver.create_distributed_write_plan(
        episode_lengths=[len(episode) for episode in EPISODES],
        episode_tasks=[
            [frame["task"] for frame in episode]
            for episode in EPISODES
        ],
    )
    session = driver.create_distributed_write_session(plan)

    ray.get(
        [
            write_one_episode.remote(spec, frames, session)
            for spec, frames in zip(plan.episodes, EPISODES, strict=True)
        ]
    )

    # Only the driver commits: it validates the artifacts and publishes meta/
    # with a recovery journal and a receipt for idempotent retries.
    driver.commit_distributed_results(session.plan, session.load_results())
    driver.finalize()


if __name__ == "__main__":
    main()
```

Start Ray first, then run the script in the driver environment:

```bash
ray start --head
python distributed_write_ray.py
```

For a remote driver, use `ray.init(address="auto")` and submit the same script
from a Ray Job or run it in the head pod. Each worker writes one independent
MP4 for each video feature selected automatically from the dataset schema.

## Failure Recovery

`DistributedWriteSession` persists the plan and one atomic success record per
worker below `<dataset-root>/.distributed-write-session/`. It does not retry
workers itself. Instead, it lets a driver, Ray Job, or external orchestrator
resume an interrupted run without repeating verified episodes.

On the first run, create the session before dispatching any workers. Pass it to
each worker writer so `save_distributed_episode()` records a result only after
the worker has finished its planned artifacts:

```python
session = driver.create_distributed_write_session(plan)

worker = LeRobotDataset.open_distributed_writer(
    REPO_ID,
    root=ROOT,
    session=session,
)
```

After a driver, worker, or cluster interruption, load the session from the same
shared root. Only dispatch the returned `pending_specs()`; completed specs with
a valid result record and valid artifacts are omitted:

```python
session = LeRobotDataset.resume_distributed_write_session(ROOT)

# Optional: clean interrupted outputs before enumerating pending episodes.
# Session-aware start_distributed_episode() also cleans its own episode.
# Stop active workers before running this global cleanup.
session.cleanup_orphaned_artifacts()

for spec in session.pending_specs():
    submit_to_your_scheduler(spec, session=session)

# When no spec remains pending, load both old and newly persisted results.
driver = LeRobotDataset.resume(REPO_ID, root=ROOT)
driver.commit_distributed_results(session.plan, session.load_results())
driver.finalize()
```

With a session, `start_distributed_episode()` acquires an exclusive lock for its
episode. If the previous attempt completed, the worker reuses its verified
result: `add_frame()` does not write the supplied frames and
`save_distributed_episode()` returns the recorded result. A spec identifies one
immutable episode; changing its input requires a new plan, not a retry. If the
previous attempt left incomplete or corrupt outputs, the worker removes only
that episode's allocated artifacts and temporary files before rewriting it.

A duplicate attempt or cleanup operation raises `filelock.Timeout` while another
process owns the episode. The scheduler may retry after that process finishes
or exits. The lock files remain outside the disposable session directory so
retries cannot acquire different locks for the same episode.

`cleanup_orphaned_artifacts()` applies the same validation and cleanup to the
whole plan. Completed results are checked against their Parquet frame ranges,
episode indices, video metadata, and SHA-256 artifact digests. Corrupt result
records make `load_results()` and `pending_specs()` fail until cleanup or a
session-aware worker retry repairs them. Writers opened without a session keep
the basic protocol and do not provide automatic retry or attempt exclusion.

After a successful commit and metadata reload, the matching session directory
is removed so the driver can plan another distributed append batch. Failed or
interrupted commits retain the session for recovery.

Metadata publication records a recovery journal before moving the old and new
`meta/` directories. Resume the session before reopening the driver after an
interruption; this completes the interrupted publication. Metadata contains a
commit receipt, so replaying the same plan and results succeeds without adding
the episodes twice, including when the driver died after publication. Conflicting
results for an already committed plan are rejected. A retained session object
can also reuse the receipt after its active session directory has been removed.

These guarantees cover process interruption. Publication uses two directory
renames and can briefly leave `meta/` absent; concurrent readers during a write
are not supported. This is not a transaction spanning all dataset files, nor a
guarantee against filesystem or machine power loss.

Do not call `commit_distributed_results()` until the session has one valid
result for every plan entry. A validation failure leaves the existing public
`meta/` directory unchanged. Always retry with the original
`DistributedEpisodeSpec`; do not create a replacement plan.

## Storage Requirements

Distributed writing supports only a local filesystem path using LeRobot's
default storage format. Direct object-store URIs and alternate storage backends
such as Lance are rejected.

All workers and the driver need access to the same dataset root at the same
absolute path. The storage must provide cross-node read-after-write visibility,
concurrent creation of distinct planned Parquet/MP4 paths, atomic file
replacement for session records, and atomic directory rename within the
dataset root for final metadata publication. Session-aware workers additionally
require cross-node advisory file locks that are released when a worker exits.
A read-write-many PVC, NFS, or a
filesystem-style object-store mount can be used only when it provides those
semantics. Node-local disks, `emptyDir`, independent `hostPath` volumes, and
direct object-store APIs without atomic rename do not satisfy this protocol.
Do not assume that an object-store FUSE/CSI volume has these semantics merely
because Kubernetes reports `ReadWriteMany`: verify immediate cross-node
visibility for newly closed files, atomic replacement, and lock exclusion first.

Use exactly one driver to create or resume the dataset, allocate the plan, and
publish `meta/`. Each `DistributedEpisodeSpec` may be owned by only one worker
at a time. Workers may run in separate processes, pods, or machines, but they
must not call `save_episode()` or write a spec assigned to another worker. A
worker must close its Parquet and MP4 outputs before publishing its session
result so the driver can validate them from shared storage.

Run the same LeRobot package version and compatible Python, PyArrow, PyAV, and
FFmpeg versions on every node. Workers load the shared dataset metadata, so
they use the same feature schema and FPS, but the scheduler must also supply
the same RGB and depth encoder configuration to every worker. Depth frames for
a given feature must use one physical unit across all episodes; the final
commit rejects worker results that report conflicting units.

Do not enable batch video encoding or streaming video encoding for distributed workers. A distributed worker writes one complete planned episode at a time.
